# Objektnivå-scopning — skrivningar mot förälder-scopade modeller

GENERERAD FIL — redigera den aldrig för hand.

En rad per fil × modell × operation. Ändras en rad har någon lagt till, tagit
bort eller flyttat en skrivning mot data som bara kan scopas via sin förälder.
Uppdatera med

    pnpm --filter @eken/api authz:objects

och säg i PR:en hur den nya skrivningen är scopad.

FILEN BEVISAR INGEN SÄKERHET. Skyddsformen är DETEKTERAD, inte verifierad —
en heuristik som säger "det här mönstret syns i funktionen", inte "id:t är
kontrollerat". Det enda filen garanterar är att ingen skrivväg tillkommer
obemärkt. Se object-scope.ts för varför mer inte går att göra statiskt.

TVÅ SKRIVFORMER INGÅR:
  DIREKT   invoiceLine + create — barnets egen accessor står i koden.
  NÄSTLAD  invoice.create({ data: { lines: { createMany: … } } }) — barnet
           skrivs via förälderns data-objekt och nämner aldrig sin accessor.
           Märks med "← nästlad via <Förälder>.<fält>". Modellen härleds ur
           schema.prisma: lines betyder InvoiceLine under Invoice och
           JournalEntryLine under JournalEntry.

Utanför: nyttolast som byggs i en annan funktion än anropet, dynamiska
fältnamn och rå SQL. Inget av det finns i kodbasen i dag — men skillnaden
mellan "finns inte" och "fångas" ska stå skriven.

FORM 1 = update/delete på ett id (den klassiska IDOR:en, #114).
FORM 2 = create med förälder-FK (ser inte ut som ett behörighetsproblem,
         men skriver in i förälderns objekt — därför bevakad).

SKYDDSFORMER:
  A  scopningen står i queryn:  findFirst({ where: { id, parent: { organizationId } } })
  B  namngiven hjälpare:        assertRelationsInOrg(orgId, { … })
  C  scopat metodanrop:         await this.findOne(id, organizationId)
  D  annan scopningsnyckel:     findFirst({ where: { id, tenantId } })  ← portalen
  P  förälderns anrop binder org: invoice.update({ where: { id, organizationId } })
     Bara nästlade rader. Den nästlade skrivningen träffar de rader föräldern
     pekar ut, så frågan är alltid om FÖRÄLDERN är bunden till anroparens org.

En form till går inte att detektera: en intern hjälpare utan aktörskontext,
där scopningen är anroparens ansvar. Den måste skrivas ner i CALLER_SCOPED med
ett påstående om vem som scopar i stället — se sista sektionen.

## Undantag: scopningen ligger hos anroparen (5 st)

Interna hjälpare utan aktörskontext. Formen är INTE automatiskt ofarlig — en
privat metod som tar ett id är exakt den skepnad en verklig IDOR gömmer sig i.
Därför står de här med ett verifierat påstående om vem som scopar i stället,
i stället för att detekteras bort.

AiTenantConversation.update  —  ai/tenant-ai.service.ts  (1 st)
    handleTextResponse(response, conversationId, message) är privat och rör bara
    updatedAt. Dess enda anropare skickar conversation.id från
    getOrCreateConversation(tenantId, …), som scopar på tenantId (form D). Id:t
    har alltså redan passerat portalens scopning innan det når hit.

UserBankIdIdentity.upsert  —  bankid/bankid-auth.service.ts  (1 st)
    enrollCollect: skrivningens EGET where är det sammansatta unika villkoret
    (provider, subjectHash, userId), och `userId` är metodens första parameter —
    den inloggades `sub` ur JWT:n, satt av controllern via @CurrentUser. Fem
    rader ovanför står CSRF-spärren: ordern bär det userId den STARTADES av, och
    collect kastar 403 när order.userId !== userId. Skrivningen kan alltså inte
    nå ett annat konto än det som både är inloggat och startade ordern.
    Heuristikens form A känner igen en bindning på find*, inte i en skrivnings
    where, och ingen av A–D är keyad på userId — därför står den här. Provet som
    bär den heter "CSRF: en ANNAN användares collect på samma orderRef NEKAS" i
    bankid-auth.service.spec.ts.

UserBankIdIdentity.deleteMany  —  bankid/bankid-auth.service.ts  (1 st)
    removeIdentity: `deleteMany where { id, userId }`, där id kommer från
    klienten och userId ur JWT:n. Avgränsningen står i skrivningen själv och är
    atomisk — därför deleteMany och inte `delete` på id:t följt av en kontroll,
    som hade haft ett fönster emellan. Träffar den noll rader kastas NotFound,
    med samma svar för "finns inte" och "tillhör någon annan". Samma osynlighet
    för heuristiken som posten ovan.

PaymentReminder.updateMany  —  notifications/payment-reminder.service.ts  (1 st)
    sendFormalReminder skriver mailJobId på markören efter commit (#357).
    Skrivningen ÄR org-bunden — `where` innehåller `invoice: { organizationId:
    invoice.organizationId }` — men heuristikens form A känner bara igen
    bindningen på find*, inte i en skrivnings where, så den syns inte.
    Invoice-objektet kommer från processOverdueReminders eget findMany; cronen
    äger alla organisationer och har ingen aktör att scopa mot. Skrivningen rör
    ett enda noteringsfält och kan inte sätta belopp, status eller kravsteg.

Unit.updateMany  —  units/unit-status.sync.ts  (2 st)
    syncUnitStatusFromLeases(db, unitId) är den enda platsen som håller
    Unit.status i synk med kontrakten (I1/#62). Den tar en prisma- ELLER
    transaktionsklient och har ingen aktörskontext alls — den kan inte scopa.
    Alla tre anropare skickar ett unitId de redan laddat: import.service
    (unit.id), leases.service (unitId i en redan org-verifierad lease-operation,
    samt lease.unitId). Skrivningen är dessutom en idempotent statussynk, inte
    en väg att sätta godtyckliga värden.

failar testet — en ny förälder-scopad modell ska inte glida in obemärkt.
