# Objektnivå-scopning — skrivningar mot förälder-scopade modeller

GENERERAD FIL — redigera den aldrig för hand.

En rad per fil × modell × operation. Ändras en rad har någon lagt till, tagit
bort eller flyttat en skrivning mot data som bara kan scopas via sin förälder.
Uppdatera med

    pnpm --filter @eken/api authz:objects

och säg i PR:en hur den nya skrivningen är scopad.

FILEN BEVISAR INGEN SÄKERHET. Skyddsformen är DETEKTERAD, inte verifierad —
en heuristik som säger "det här mönstret syns i funktionen", inte "id:t är
kontrollerat". Filen garanterar att ingen skrivväg via en modells EGEN
Prisma-accessor (invoiceLine + create) tillkommer obemärkt — inte mer än så.
Se object-scope.ts för varför mer inte går att göra statiskt.

INTE BEVAKAT: NÄSTLADE SKRIVNINGAR. En skrivning som går via förälderns
data-objekt — invoice.create({ data: { lines: { createMany: … } } }) — nämner
aldrig barnets accessor och syns därför inte här. Sju sådana ställen finns i
kodbasen (JournalEntryLine ×3, InvoiceLine ×4); de är manuellt granskade
2026-08-02 och listade med fil:rad i object-scope.ts. Att InvoiceLine och
JournalEntryLine står klassificerade längst ned betyder alltså INTE att deras
skrivyta är komplett här. En ny nästlad skrivning larmar inte.

FORM 1 = update/delete på ett id (den klassiska IDOR:en, #114).
FORM 2 = create med förälder-FK (ser inte ut som ett behörighetsproblem,
         men skriver in i förälderns objekt — därför bevakad).

SKYDDSFORMER:
  A  scopningen står i queryn:  findFirst({ where: { id, parent: { organizationId } } })
  B  namngiven hjälpare:        assertRelationsInOrg(orgId, { … })
  C  scopat metodanrop:         await this.findOne(id, organizationId)
  D  annan scopningsnyckel:     findFirst({ where: { id, tenantId } })  ← portalen

En femte form går inte att detektera: en intern hjälpare utan aktörskontext,
där scopningen är anroparens ansvar. Den måste skrivas ner i CALLER_SCOPED med
ett påstående om vem som scopar i stället — se sista sektionen.

## Undantag: scopningen ligger hos anroparen (2 st)

Interna hjälpare utan aktörskontext. Formen är INTE automatiskt ofarlig — en
privat metod som tar ett id är exakt den skepnad en verklig IDOR gömmer sig i.
Därför står de här med ett verifierat påstående om vem som scopar i stället,
i stället för att detekteras bort.

AiTenantConversation.update  —  ai/tenant-ai.service.ts  (1 st)
    handleTextResponse(response, conversationId, message) är privat och rör bara
    updatedAt. Dess enda anropare skickar conversation.id från
    getOrCreateConversation(tenantId, …), som scopar på tenantId (form D). Id:t
    har alltså redan passerat portalens scopning innan det når hit.

Unit.updateMany  —  units/unit-status.sync.ts  (2 st)
    syncUnitStatusFromLeases(db, unitId) är den enda platsen som håller
    Unit.status i synk med kontrakten (I1/#62). Den tar en prisma- ELLER
    transaktionsklient och har ingen aktörskontext alls — den kan inte scopa.
    Alla tre anropare skickar ett unitId de redan laddat: import.service
    (unit.id), leases.service (unitId i en redan org-verifierad lease-operation,
    samt lease.unitId). Skrivningen är dessutom en idempotent statussynk, inte
    en väg att sätta godtyckliga värden.

failar testet — en ny förälder-scopad modell ska inte glida in obemärkt.
